# 64-bit PC port: working notes

Handoff notes for the `make pc64` build (x86_64, `PC_BITS=64`, output in
`build/pc64_USA/`). The 32-bit build (`make pc`, `build/pc_USA/`) is the
reference: it behaves like the GBA because pointers are 4 bytes. The goal is
for the 64-bit build to behave identically.

See `PC.mk`, `tools/pc/gen_linker.py`, `tools/pc/ram_commons.py` and
`tools/pc/agbcc_layout.py` for how the 64-bit build lays out memory.

## How to find 64-bit bugs

Run both builds headless with the same scripted input and compare.

Useful environment variables (`src/platform/pc/main.c`):

- `TMC_HEADLESS=1`: no window.
- `TMC_FRAMES=N`: exit after N frames (exit code 0, prints `tmc: ran N frames`).
- `TMC_INPUT="400:a,430:start,..."`: press keys for 4 frames starting at each frame.
  Key names: `a b select start right left up down r l menu`.
- `TMC_SCREENSHOTS="100,200,..."`: write `shot_<frame>.bmp` in the cwd.
- `TMC_LOG_OPENBUS=1`: log NULL-page accesses emulated by `openbus.c`.

Each run writes `tmc.sav` in the cwd, so run each build in its own empty
directory, and delete `tmc.sav` between runs.

The input used so far (title screen, file select, new file, name entry):

```sh
IN=$(python3 -c "print(','.join(f'{f}:{\"start\" if f%60==0 else \"a\"}' for f in range(400,6000,30)))")
```

### Compare hardware state

Hardware memory stays at GBA addresses in both builds, so it can be compared
byte for byte. Stop at `exit` in gdb and dump it:

```sh
TMC_HEADLESS=1 TMC_FRAMES=$N TMC_INPUT="$IN" gdb -q -batch \
  -ex 'handle SIGSEGV nostop noprint pass' -ex 'break exit' -ex run \
  -ex 'dump binary memory vram.bin 0x06000000 0x06018000' \
  -ex 'dump binary memory oam.bin 0x07000000 0x07000400' \
  -ex 'dump binary memory pltt.bin 0x05000000 0x05000400' \
  build/pc64_USA/tmc
```

`SIGSEGV` must pass through: `openbus.c` handles it.

I/O registers 0xB0-0xD6 (DMA source and destination) always differ, since RAM
addresses differ. Everything else should match.

### Compare game RAM

RAM variables are not at GBA addresses in the 64-bit build, so compare them by
symbol (`dump binary value gBG1Buffer.bin gBG1Buffer`). Only types without
pointers compare byte for byte.

### Find the writer

Once a variable differs, set a watchpoint in the 64-bit build:

```sh
gdb ... -ex 'break <function that sets it up>' -ex run \
  -ex 'watch -l *(unsigned short*)((char*)&gBG1Buffer+0x1f2)' -ex continue -ex bt
```

## Bug classes to look for

- Code that walks adjacent RAM variables as one array, or uses one variable's
  address as the end of another. In the 64-bit build each RAM variable is a
  separate common, placed in any order (`ram_commons.py`).
- Structs used as slots of another struct's size. On the GBA they match; with
  8-byte pointers they may not.
- Hardcoded sizes (`MemClear(&x, 10880)`) instead of `sizeof`.
- Pointers stored in `u32` fields, or compared through `(int)`/`(u32)` casts.

## Changes in this session (2026-10-17)

### Entity slots made contiguous

Symptom: on the name entry screen, keyboard letters were missing (64-bit only,
from about frame 540 with the input above).

Cause: on the GBA, `gPlayerEntity` (0x03001160), `gAuxPlayerEntities` (7 slots)
and `gEntities` (72 slots) are adjacent, each slot `sizeof(GenericEntity)`
(0x88). The game walks them as one `GenericEntity[80]` array:

- `ClearAllDeletedEntities` (`src/entity.c`): from `&gPlayerEntity` for 80 slots.
- `CreateEntity` (`src/entity.c`): from `&gPlayerEntity` up to `&gCarriedEntity`,
  the variable after `gEntities` on the GBA.

In the 64-bit build the three were separate commons in any order
(`gPlayerEntity` came after `gEntities`, just before `gBG1Buffer`), and
`PlayerEntity` (184 bytes) is smaller than `GenericEntity` (208 bytes). So
`ClearAllDeletedEntities` saw `gBG1Buffer` data as deleted entities and cleared it.

Fix:

- `src/platform/pc/memory.c`: in the 64-bit build, define one static struct
  `sEntitySlots` (player slot as a union of `PlayerEntity` and `GenericEntity`,
  then the aux and entity arrays) in section `.gba_ram`. Top-level extended
  asm sets `gPlayerEntity`, `gAuxPlayerEntities` and `gEntities` to its parts.
  An alias cannot point at a common symbol, so the storage is a real
  definition.
- `tools/pc/gen_linker.py`: `PLATFORM_RAM` lists the three names. They are left
  out of `ram_symbols.txt` (so `ram_commons.py` keeps their C declarations
  `extern`) and out of `ram_symbols.s`. The `.gba_ram` output section now takes
  `*(.gba_ram)` before `*(COMMON)`, so `RegisterRamReset` still clears them.
- `src/entity.c` (`CreateEntity`): end bound `(GenericEntity*)&gCarriedEntity`
  changed to `&gEntities[MAX_ENTITIES]`. This is the same address on the GBA.
  The GBA build was not checked for matching (no ARM toolchain here).

Verified: `nm build/pc64_USA/tmc` shows the three symbols contiguous at a 0xD0
stride inside `__gba_ram_start`/`__gba_ram_end`. Keyboard letters now match the
32-bit build (frame 600 screenshot).

### gMoreSpritePtrs entries were 40 bytes

Symptom: on the name entry screen, the cursor marker above the name field and
the icon left of it were missing (64-bit only, from about frame 540). The OAM
was the 32-bit OAM shifted down by one entry.

How it was found: walking `gEntityLists` in gdb at frame 550 in both builds
(print kind, id, type, frameIndex for each entity) showed `FILE_SCREEN_OBJECTS`
types 9, 15, 16 and 17 with `frameIndex=0xFF` in the 64-bit build. They start
an animation with `InitAnimationForceUpdate`, which reads
`gSpritePtrs[325].animations`. In the 64-bit build that was NULL, and the
pointer had landed in `pad`.

Cause: in `data/gfx/sprite_ptrs.s`, the 7 entries after `gMoreSpritePtrs`
(sprites 322-328) wrote the `u32 pad` field and the 64-bit padding with `ptr`
(8 bytes each) instead of `.4byte`. Each entry was 40 bytes instead of
`sizeof(SpritePtr)` (32), so every entry after sprite 322 was misread. The
entries before `gMoreSpritePtrs` were already correct.

Fix: those two fields are `.4byte` again, as in the other entries. The 32-bit
build is unchanged: there, `ptr` is 4 bytes. Under `PLATFORM_PC64`, an `.error`
check after the table fails the build if the table is not 329 * 32 bytes.

Verified: `gSpritePtrs[322]` and `[325]` read correctly in gdb. With the input
above, all screenshots every 100 frames up to frame 6000 match the 32-bit
build. No open bus log differences.

## Static data audit: tools/pc/data_audit.py

Playing through the game to find divergences is too slow. Most 64-bit bugs so
far are data laid out wrong for its C type, which can be checked for the whole
ROM at once:

```sh
python3 tools/pc/data_audit.py build/pc_USA/tmc build/pc64_USA/tmc [--all] [--check]
```

For each symbol defined in `data/` or `asm/` that C declares with a type, it
converts the 32-bit build's bytes to the 64-bit layout of that type and
compares them with the 64-bit build's bytes, field by field. Pointers must
point at the same symbol and offset (mapped into the target's 64-bit layout).
4-byte fields may differ only by holding the same symbol's address. It runs in
about 30 seconds. `layout_audit.py` only compares sizes and missed the
`gMoreSpritePtrs` bug. This audit finds that class.

Heuristics, to keep false positives down (see the code for details):

- An array's element count is its span up to the next symbol, bounded by the
  end of its input section (from the 32-bit `.map`). Untyped symbols right after
  an array whose elements contain pointers count as more elements, if they are
  contiguous in both builds (`gSpritePtrs` and `gMoreSpritePtrs`).
- In a top-level array of pointers, the first element that holds no address
  ends the table.
- Values below 0x10000000 outside GBA RAM (VRAM addresses, numbers) are not
  mapped: they must be equal.
- Scalar arrays (scripts are `u16[]`) are compared word by word, allowing
  32-bit addresses at 2-byte alignment.
- Symbols declared with different types in the two builds' debug info are
  listed and skipped.

### Last result: 9 symbols with differences (none fixed yet)

1. `Area_HyruleTown` (`src/roomInit.c`: `extern u32 Area_HyruleTown[]`) and
   `gSpriteAnimations_GhostBrothers` (`src/npc/ghostBrothers.c`:
   `extern u32 ...[]`): the data is `ptr` (8 bytes), but C indexes it as
   `u32`, so element n > 0 reads the wrong half. Fix: declare them as pointer
   arrays (`void* []`), and update the casts in the code that uses them.
2. `EntityData.spritePtr` (`include/room.h`, `uptr`): 5 records where the GBA
   data holds a number there (`gUnk_080F3494`, `gUnk_080F4B88`,
   `gUnk_080F5B3C`, `gUnk_080FEE58`): 0x8000005F, 0xCE (an `ezlo_hint`
   flag), 0x570000. In the 64-bit build, the entity macros
   (`asm/macros/entity.inc`, `entity_record_pad`) keep the GBA's 16 bytes and
   append 8 zero bytes. So GBA offset 12-15 lands in padding (64-bit
   `spritePtr` is at offset 16), and C reads 0. `src/room.c:140` reads
   `spritePtr` as a script pointer for some kinds. Check which entity kinds
   read the low word as a number (`ezlo_hint`: flag), and either copy those
   bytes to offset 16 in the macros or read them where the 64-bit layout puts
   them. The generated `data/pc64/*.inc` files for these symbols need the same
   rule (`tools/pc/gen_pc64_data.py`).
3. `gUnk_080E4C08`: C declares `Entity` (`templeOfDropletsManager.c`) but it is an
   `EntityData` list (it is cast to `EntityData*`). `data/pc64/gUnk_080E4C08.inc`
   was generated from the `Entity` type, which moved bytes
   (`spriteVramOffset`, `spriteOffsetX/Y` differ). Fix the C declaration to
   `EntityData[]` and regenerate.
4. `gUnk_080D8E50` (`struct_080D8E54[]`, generated `.inc`): elements 6-7
   differ. It may be the count (the 32-bit span may include other data) or
   a real conversion error. Check the element count used in
   `src/roomInit.c:1010`.
5. `gUnk_080F0CB8` (`extern Entity* gUnk_080F0CB8[15]`, only 8 `ptr` entries in
   the data, indexed `& 0xF`): on the GBA, indexes 8-14 read the next data
   (`gUnk_080F0CD8`). The 64-bit build reads different bytes there. Check
   which indexes the game uses.
